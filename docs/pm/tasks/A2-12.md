## 这条任务是怎么来的

A2-03（PR #113，已合入）把 `kda_fwd_stable` 与 `kda_fused_recurrent` 两个单元原样移植到 A2，用 20 + 8 个契约 case
和一个 (C∈{1,2}) × (HV∈{1,2,4}) × (bd∈{1,2}) = 12 格网格在 910B3 上过了 reference / sim / pipesim / 真机四条流水线，
但**明确留了两件事没做**（A2-03 DONE 原文）：「契约 board stage untested，门控跨度闸
`recommended_limit=null`（**A2-12 重测**）」——真实形状（`docs/matrix/models.json` 的 Kimi-Linear-48B-A3B：
`H=HV=32, K=V=128`）也没有跑过，因为 20 个契约 case 用的是 `(C,HV)` 网格里的小形状，不是真实模型尺寸。

`ascend_fla/platform.py` 的 `CAPABILITIES` 表现在是这样（AGENTS.md §6「结论不跨 SoC 继承」的具体落地）：

```python
CAPABILITIES = {
    "a5": {"qualified": True, "supported_block_dim": {...}, "max_gate_span": {...}, ...},
    "a2": {"qualified": False, "supported_block_dim": {}, "max_gate_span": {}, ...},  # 本任务要填这个
    ...
}
```

A2 的入口调用现在因为 `qualified=False` 而直接报错（这是对的，§7 门控纪律）。本任务做完之后，
`CAPABILITIES["a2"]` 应该填上**实测**的 `supported_block_dim`（chunk 路径；decode 不在本任务范围，
`kda_fused_recurrent` 的门控跨度另算，若来不及可以只交 chunk 的、把 decode 记成已知缺口）与
`max_gate_span`（chunk 路径，`stable` 一档，按 A5 同名字段的口径：`impl → direction → 数字`，本任务只有
`forward`，`backward` 留 `None` 或干脆先不加那一层，由 PM 在合并时定字段形状）。**在这张表被真实数字填上之前，
`qualified` 必须留 `False`**——不要因为跑通了几个 case 就手滑改成 `True`；`qualified=True` 是本任务验收过、
PM 审过之后才由 PM 改的最后一步，不是 assignee 自己翻的开关。

## 范围

1. **真实形状**：用 `docs/matrix/models.json` 的 Kimi-Linear 真实参数（`H=HV=32, K=V=128`，`T` 取
   `L_PER_CHUNK` 的整数倍——64、128、256、512、4096 至少各一个）在 A2 真机上跑 `kda_fwd_stable`
   （`benchmarks/verify_real_shapes.py` 的现有 A5 逻辑照抄形状生成部分，换 `device`/`soc` 参数），
   对 CPU FP32 参考（`ascend_fla/reference/kda.py`）报 `o` / `final_state` 的相对 L2，预算沿用
   `kda_fwd` 契约的 `0.05`（A2-03 用的同一个数，不新定）。
2. **门控跨度重测（chunk / forward）**：`H=HV=32` 真实形状下，按 AGENTS.md §6「按量程失效的缺陷」与
   「闸是双边约束」两段的方法论——**方法论可以借，阈值必须在 A2 上重测，不能抄 A5 的 155**：
   - 用 `tests/test_kda_gating.py` 里 A5 版本的 `_calibrate_span` 思路（平移 `A_log` 把跨度确定性地标定到目标值），
     在 A2 上从小到大扫 `gate_span`，每个点报 **两件事分开报**：①输出是否有限（`finite`），②对 CPU FP32
     参考的相对 L2 是否在预算内（`ok`）。
   - 上边界：预算仍然成立的最深实测点（不是"刚好还没炸"的那个点，要往回留出安全边界，参照 A5 155 vs
     有限性 169.8 的留白比例，具体数字由实测决定、不预设）。
   - 下边界：fla 默认初始化（`A_log = log(U(1,16))`）在真实 `HV=32` 形状下、多个随机种子（≥8，同 A5 的口径）
     实测到的跨度分布上界——**不能只测一个 seed 就当默认值**，AGENTS.md §6 已经踩过这个坑。
   - 两个边界都要写实测依据；闸最终定成 `min(上边界所有安全点)`，不能只看下边界"过得去"就定高。
3. **(C, HV) 网格**：A2-03 已经跑过 `HV∈{1,2,4}`；本任务把 `HV=32`（真实值）也纳入网格的边界检查。

   **2026-09-23 更正（申领人在 #39 的两条 RISK 指出、PM 读源码核实，原文写错了）**：
   `c1-multihead-o-corrupt` 的成因是 A5 `kda_fwd_stable`（严格说是它更早的 `upstream` 版）Aqk 的
   两信用固定槽轮转与实际周期数不匹配；`ascend_fla/ops/kda/chunk.py:387`
   （`_check_recurrent_heads`）里这条拒绝只对 `impl == "upstream"` 生效——`impl == "stable"`
   直接跳过检查，**因为 stable 已经是修过的单元，不会踩这个坑**。A2 的
   `kernels/projects/a2/kda_fwd_stable` 这条差别更大：它的 Aqk 交接架构根本不同（每个 chunk 载入
   cube 本地缓冲，不是 A5 那种共享 L1 环），README「与 A5 版本的差别」第 5 条明写"A5K-01 修的
   Aqk L1 轮转信用在这个设计里不存在"，并且 A2-03 已经在真机与仿真上验证过 **C=1 多头、奇数 C
   逐位正确**。所以：
   - **`C=1` 且 `HV=32` 不预期报错**，按正常数值 case 处理——对 CPU FP32 参考报相对 L2，预算同上；
   - 这一格反而是本任务的一个重点正例（A2-03 只测到 `HV≤4`，没测过 `HV=32` 这种远超 `block_dim`
     声明值的组合，值得作为独立 case 单独报数字，不要和别的形状混在一批平均里）；
   - 唯一还需要"确认拒绝"的地方是 `impl='upstream'` 路径本身（如果测试代码会经过它的话）——
     但 A2-12 的写集只涉及 `kda_fwd_stable`，不涉及 `upstream`，所以正常情况下不会触发这条检查，
     不需要专门为它写测试。
4. **`CAPABILITIES["a2"]` 填数**：真实形状 + 门控跨度两项都过了之后，把实测的 `supported_block_dim`（chunk：
   目前已知安全值是 A2-03 测过的 `{1, 2}`，本任务不必扩大它——`block_dim` 上限本身是另一个课题，超出范围就
   如实写"未测更大值"，不要顺手去试）与 `max_gate_span["stable"]["forward"]` 写进
   `ascend_fla/platform.py` 的 `CAPABILITIES["a2"]` 字典；`qualified` 仍留 `False`（PM 审过再改）。
