## 这条任务是怎么来的

A2-07 把 Qwen3-Next 要用的 GDN 与现有 A5 派生单元（GDA-01/02/03、BF-01/02）逐项对过，列出六个 ABI 缺口
与它们在 A2-01 命中表里的 split-K/L0C-settle 暴露面，并给出三段批次划分。**这是 Batch A**：把
`gdn_chunk_{fwd,bwd}` 搬到 A2，同时补齐 ABI 缺口、加上 barrier(Pipe.M) 绕行。A2-11 已经把这条绕行本身
在真机上验证过（`tests/test_a2_accumulate_barriers.py` 的静态守卫覆盖全部 `kernels/projects/a2/**`，
包括本任务新建的两个单元——不需要新写守卫，新单元自动被扫到）。

## 范围（严格对齐 `a2_gdn_abi.md` §1.1–1.7 与 §2，不要重新分析，直接实现）

**六个 ABI 缺口**（详细的现状/修法/风险/验证已经在 A2-07 文档里逐条写清，照做）：

1. **§1.1 GQA/GVA（`gdn-no-gqa`）**：v/state/output 带 `HV` 轴、q/k 侧仍 `H` 轴，组内 in-kernel head
   indexing 复用 GDA-02 的模板（`i_h = i_hv // (HV//H)`）。验证用 `H≠HV`（如 H=2, HV=4）且组内取值
   彼此不同的 case，错误的 `i_h` 必须测出来。
2. **§1.2 token-major 布局**：公共入口 token-major、内部按需要 permute 成 kernel 友好布局；permute
   必须是真实 materialize，不是跨步 view（A2 上跨步 Slice 不一定可用，参照 AGENTS.md §5 的 D2H 教训，
   这里是同理的"先整理布局再进 kernel"原则）。
3. **§1.3 非零 initial_state**：接受 FP32 `[B,HV,128,128]` 的非零初始 state（同 KDA 的做法）。
4. **§1.4 反向产出 `dh0`**：反向递推emit `dh0`、接受 `dht`（同 `kda_bwd`）。
5. **§1.5 `final_state` FP32**（不是上游的 BF16）：这是本批次唯一带数值风险的一项——bf16→fp32 state
   在 A2 上的实际改善幅度**未测**，不能照抄 A5 的结论；同形状分别建 bf16-state 版与 fp32-state 版对
   fp32 递推 oracle，报两版的相对 L2 差多少（这个数字进 evidence，不是拿来当验收阈值，只是留证据）。
6. **§1.7 scale 参数 + no-tail-path**：加 `scale: f32` 标量，在 q 读入处吸收；`T` 必须是 64 的倍数，
   不满足显式拒绝（不要做真正的 tail path，那是更大的改动，不在本批次）。

**L0C settle（A2-01 §8 W2/W4，A2-07 §2 精确定位）**：

- `gdn_chunk_fwd` 的 inverse 阶段（对应 A5 `gdn_fwd/kernels/inverse.py:306/312/317-318`，HIT-B，
  FP32 手写链，M16，未 settle）与 `gdn_chunk_bwd` 的 finalize 阶段（对应 A5
  `gdn_bwd/kernels/finalize.py:205/217/226/235/244`，同类）：**每个 L0C 累加 MMAD 前都要
  `barrier(Pipe.M)`，不分 dtype**——这正是 A2-11 已经在真机上验证过、且现在写进 `AGENTS.md` §7 的
  永久纪律（BF16/FP16 的 `splitk` 在 `M<64` 必须显式报错，不能出现在任何可达路径）。
- `gdn_chunk_bwd` 的 wu 阶段（对应 A5 `gdn_bwd/kernels/wu.py:206`，BF16 chain，M64）：同样加 barrier；
  M64 本身在 A2-11 的真机实测里是安全的（199/200 逐位正确），但 barrier 仍要加——**不是因为 M64 不安全，
  是因为"每个累加 MMAD 前都有 barrier"是本仓现在的统一纪律，不按测出来的安全边界开例外**。
- 其余阶段（preprocess/recompute/scores/recurrent/scan_local/inverse_preprocess/recurrent_saved）在
  A2-07 的命中表里是 MISS（各自的 MMAD 各自 init 自己的 L0C），不需要 barrier，但**照样要跑一遍
  `tests/test_a2_accumulate_barriers.py`（本仓已有的静态守卫，扫全部 `kernels/projects/a2/**`）确认
  没有漏判的 `is_init=False` matmul**——这条测试不用新写，交付时它自动覆盖新文件。

## 不在本批次的范围（Batch B / C，明确排除）

- **门控跨度标定**（`a2_gdn_abi.md` §3 已经给出量程分析：真正的约束是 `exp(+span)` 与 `1/eg` 在
  span≈88.7-89 溢出，不是 `eg→0` 的 104；A2 不冲刷 FP32 subnormal，这点与 A5 不同，不能沿用 A5 的
  87.3/155/105）——**这是 Batch B，另立任务**。本批次的 kernel 测试只用小、明确安全的 gate span
  （比如 span ≤ 10，远离 88.7 的临界区），不测边界、不定 `MAX_GATE_SPAN` 的具体数字，`platform.py`
  的 `CAPABILITIES["a2"]` 里 GDN 的门控跨度字段留空或标"未测（Batch B）"。
- **decode kernel**（`fused_recurrent`）——这是 `GDA-04`（已存在的骨架任务），依赖本任务但本任务不做它。
- 与本批次无关的 A2 单元（KDA 系列）不要碰。

## 已知陷阱

- **内部 kernel 形参名避开 C++ 关键字**：`do`、`in`、`class` 等——GDA-03 与 PK-05 都提醒过这条，
  这是第三次写进规格，说明这个坑真的容易踩，务必检查全部新增 kernel 的形参名。
- **一个算子名一个进程一份 build**（AGENTS.md §6 铁律二）：新建的两个单元每个 kernel 要有自己的算子名，
  不要因为是"从 A5 搬过来的"就沿用 A5 单元的算子名——BF-05 刚在这一条上踩过坑（同进程两条路径共存时
  静默拿到错误的二进制），参照它的修法（kernel 函数名加后缀区分）。
- **A2 的核数是 20 cube / 40 vector**（不是 A5 的 32/64），`block_dim` 上限未测，不要假设任何数字。
- 机器与卡归 assignee 自己管理（D-PM-28）。
