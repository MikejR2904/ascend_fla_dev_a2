## 这条任务是怎么来的

PK-03 交付的是正确的、已过真机验收的 PGDN chunk 前向（FP32+BF16），性能优化明确不在它的范围
内。用户直接要求开这条优化任务。

**当前已知的基线数字**（PK-03，A5 真机，三轮同卡同步三明治，1800 个原始样本，
`docs/pm/board.json` PK-03.result.numbers，`kernels/projects/a5/pgdn_chunk_fwd/evidence/native/
README.md`）：

| 形状 B1/H=HV=8/K=V=128 | "GDN 方程成本基线"（同 5 个 kernel、key 相同、关掉 ATK） | PGDN 候选 | 比值 |
|---|---|---|---|
| T=4096, FP32/BF16 | ≈547.7–547.9 ms | ≈566.3–566.9 ms | **慢 3.4%** |
| T=1024, FP32/BF16 | ≈137.8–137.9 ms | ≈143.6–144.1 ms | **慢 4.2%–4.5%** |

**这个基线不是 torch_npu 组合算子、不是 GDA-02 的真实 GDN 性能**——它是"同样 5 个 PGDN kernel、
关掉 ATK、key 读写相同"的人造对照（仓库原话："This baseline is not the GDA-02 implementation, nor
a semantically equivalent PGDN algorithm"）。它存在的目的是**隔离出 ATK 预条件本身的开销**：
两者唯一的算法差异就是 ATK 开/关，所以这 3.4%-4.5% 的差距，第一直觉就是"ATK 预条件本身的代价"，
但**这是推断，不是 profile 结论**——GDA-05 的范围骨架里写的"PK-03 的 T=4096 前向约 566 ms，其中
ATK 是逐 token 串行；先量出各阶段占比，别凭这一个数字下结论"就是在提醒这一点：ATK 逐 token串行
是一个可疑点，不是已确认的瓶颈，stage 级占比还没真正量出来。

## 依赖关系：为什么要等 GDA-05

`GDA-05`（issue #96，当前 `assigned`）正在对六个既有实现（含本任务的 PGDN chunk 前向 / PK-03）
做**设备侧/host 侧拆分的 stage 级 profile**，而且写集里不碰 `kernels/projects/a5/pgdn_chunk_fwd/**`
——两者文件不冲突，但**逻辑上重复**：如果本任务（PK-08）自己重新测一遍 PK-03 的 device/host
拆分基线，就是在和 GDA-05 做同一件事,两份数据还可能因为环境/批次不同而不一致，白白浪费真机
时间。

**因此**：PK-08 在 GDA-05 交出 PGDN chunk 前向的 profile 报告（`docs/research/gda05_profile.md`）
之前，**不要开始真机测量**——直接复用 GDA-05 的 device/host 拆分结论作为本任务的起点基线，
不要重新测一遍。PM 会在 GDA-05 的 DONE 审查通过后，把具体的 profile 数字摘要同步进本文件，
到时候状态会从"等依赖"变成可以真正开工。

**如果有人在 GDA-05 完成前 APPLY 本任务**：按协议 NO_TASK，理由是依赖未满足（同 GDA-05 自己
当年等 PK-06 合入时的处理方式），不要因为写集不冲突就当作可以并行开工——数据依赖比文件依赖
更要紧。

## 范围（GDA-05 完成后生效）

1. **先看 GDA-05 的 stage 级数字，不要自己先猜**（AGENTS.md §6 铁律一）：确认 ATK 逐 token
   串行是否真的是主要耗时项、占比多少，还是别的 stage（q/k 归一化、state 分配、output cast）
   占比更大。**第一步只是读数据、定问题，不是立刻动手改代码。**
2. 如果 GDA-05 的数据确认 ATK 预条件是主要开销：
   - 判断是否有不破坏数学等价性的并行化空间（当前实现逐 token 串行是否有算法必要性，还是
     实现层面可以批处理/向量化——这需要读 `kernels/projects/a5/pgdn_chunk_fwd/` 源码确认，
     不要假设"看起来能并行就能并行"）。
   - **一次只改一处**（AGENTS.md §6 铁律二），每次改动都要和 GDA-05 的基线数字做同条件对照
     （同形状、同 `bd`、同卡同步三明治）。
3. 如果 GDA-05 的数据显示 ATK 不是主要开销（推翻了上面的直觉）：如实记录这个发现，
   **按 profile 结果重新定目标**，不要硬找"ATK"当靶子——GDA-05 验收判据第三条就是"报告里不下
   优化建议的结论，只给数字"，PM 会根据实际数字另定目标，这里不预支结论。
4. 每改一处，重跑契约 case（`bd` 跨进程逐位对比）+ 正确性（FP32 判定 + BF16 质量检查）+
   静态/sim 诊断，同 PK-07 第 3 步的纪律。
5. 性能验收：真实形状上同卡同步三明治，对照 GDA-05 的基线数字（不是 PK-03 报告里的
   T1024/T4096 玩具数字）。
