## 这条任务是怎么来的

PK-03 交付的是正确的、已过真机验收的 PGDN chunk 前向（FP32+BF16），性能优化明确不在它的范围
内。用户直接要求开这条优化任务。

**2026-10-16 写集扩大说明**：原规格的写集只有 `kernels/projects/a5/pgdn_chunk_fwd/**`（FP32），
明确排除了 `pgdn_chunk_fwd_bf16/**`（当时理由是"BF16 是 BF-03 的写集"）。GDA-05 的申领人在交付
DONE 时指出：`ascend_fla/ops/pgdn_chunk_fwd.py:139` 的公开入口按 `q.dtype` 把 BF16 输入分派到
`_bf16_pipeline()`（对应 `kernels/projects/a5/pgdn_chunk_fwd_bf16/kernels`），FP32 分派到
`_pipeline()`（对应 `kernels/projects/a5/pgdn_chunk_fwd/kernels`）——这是两个完全独立的 kernel
目录，不是同一套代码同时处理两种 dtype。PM 读源码核实属实。按用户的标准优先级（D-PM-35"BF16
优先"），本任务的写集扩大为同时覆盖两个目录，不再人为排除 BF16 路径。

**当前已知的基线数字**（PK-03，A5 真机，三轮同卡同步三明治，1800 个原始样本，
`docs/pm/board.json` PK-03.result.numbers，`kernels/projects/a5/pgdn_chunk_fwd/evidence/native/
README.md`）：

| 形状 B1/H=HV=8/K=V=128 | "GDN 方程成本基线"（同 5 个 kernel、key 相同、关掉 ATK） | PGDN 候选 | 比值 |
|---|---|---|---|
| T=4096, FP32/BF16 | ≈547.7–547.9 ms | ≈566.3–566.9 ms | **慢 3.4%** |
| T=1024, FP32/BF16 | ≈137.8–137.9 ms | ≈143.6–144.1 ms | **慢 4.2%–4.5%** |

**这个基线不是 torch_npu 组合算子、不是 GDA-02 的真实 GDN 性能**——它是"同样 5 个 PGDN kernel、
关掉 ATK、key 读写相同"的人造对照（仓库原话："This baseline is not the GDA-02 implementation, nor
a semantically equivalent PGDN algorithm"）。它存在的目的是**隔离出 ATK 预条件本身的开销**：
两者唯一的算法差异就是 ATK 开/关，所以这 3.4%-4.5% 的差距，第一直觉就是"ATK 预条件本身的代价"，
但**这是推断，不是 profile 结论**——GDA-05 的范围骨架里写的"PK-03 的 T=4096 前向约 566 ms，其中
ATK 是逐 token 串行；先量出各阶段占比，别凭这一个数字下结论"就是在提醒这一点：ATK 逐 token串行
是一个可疑点，不是已确认的瓶颈，stage 级占比还没真正量出来。

## 依赖关系：为什么等了 GDA-05（已满足）

`GDA-05`（issue #96，已 done）对六个既有实现（含本任务的 PGDN chunk 前向 / PK-03）做了
**设备侧/host 侧拆分的 stage 级 profile**，而且写集里不碰 `kernels/projects/a5/pgdn_chunk_fwd/
**`——两者文件不冲突，但**逻辑上重复**：如果本任务（PK-08）自己重新测一遍 PK-03 的 device/host
拆分基线，就是在和 GDA-05 做同一件事，两份数据还可能因为环境/批次不同而不一致，白白浪费真机
时间。这就是为什么要等它合入再定目标，而不是两边并行猜。

**2026-10-17 更新（GDA-05 已合入，数字已定稿）**：PR #143 → `4c286d5b`，`docs/research/
gda05_profile.md`（SHA256 `5f5ffce8b88b7a96d7e4cb9806edc23ab562c1a0a7b5d37b1c10e24c25de7589`）
是正式基线，不再是预览数字。**结论：ATK 不是主要开销，之前的"直觉"被推翻**——

`pgdn_fwd`，真实形状 `t4096_h16_hv32`（`models.json` 的 `qwen3_next_layer`），bd=1 与 bd=2
两份独立 build 的占比几乎相同（下表为 bd=1，中位数，占 kernel 总和 %）：

| native entry | BF16 | FP32 |
|---|---:|---:|
| atk | 1.286% | 1.399% |
| prepare | 0.809% | 0.937% |
| **scores** | **38.284%** | **38.177%** |
| wy | 15.072% | 15.023% |
| scan | 10.833% | 10.815% |
| **output** | **33.656%** | **33.578%** |
| 其余设备算子 | 0.055% | 0.069% |

`atk`+`prepare` 合计只占 ≈2.1%–2.3%，bd=1/bd=2 一致，BF16/FP32 一致——ATK 预条件本身的代价
在真实形状下微不足道，PK-03 那 3.4%–4.5% 的"基线差距"不能归因于 ATK（GDA-05 的报告本身不下
这个结论，这是 PM 看数字后的判断，仍需本任务自己验证）。**`scores`（≈38%）与 `output`
（≈33.6%）合计占了约 72% 的 kernel 时间，是目标候选**；`wy`（≈15%）、`scan`（≈11%）是次要
候选。

## 范围

1. **先确认 scores / output 两个 native kernel 具体在算什么、能不能动**（AGENTS.md §6 铁律一，
   不要先猜）：读 `kernels/projects/a5/pgdn_chunk_fwd/` 源码里 `pgdn_chunk_scores` /
   `pgdn_chunk_output`（BF16 对应 `pgdn_bf03_scores` / `pgdn_bf03_output`）的实现，判断是否有
   不破坏数学等价性的改动空间（算子选择、数据重排、是否有可消除的冗余计算），不要假设
   "占比高就等于能优化"——占比高也可能是因为这一步本身计算量就大（FLOPs 绑定），那就不是
   bug，是物理上限。
2. **一次只改一处**（AGENTS.md §6 铁律二），每次改动都要和 GDA-05 的基线数字做同条件对照
   （同真实形状、同 `bd`、同卡同步三明治）——不是跟 PK-03 报告里的玩具形状比。
3. 如果读源码后发现 scores/output 没有改动空间（物理上限），如实记录，再看 wy/scan；
   不要为了"有改动"而硬改一个占比高但实际已经最优的 kernel。
4. 每改一处，重跑契约 case（`bd` 跨进程逐位对比）+ 正确性（FP32 判定 + BF16 质量检查）+
   静态/sim 诊断，同 PK-07 第 3 步的纪律。
5. 性能验收：真实形状上同卡同步三明治，对照 GDA-05 的基线数字（不是 PK-03 报告里的
   T1024/T4096 玩具数字）。

## 已知陷阱

- **ATK 不是瓶颈，这是已核实的 profile 结论，不是待验证的直觉**——不要再去优化 ATK 本身；
  目标是 scores/output（合计≈72%），次要是 wy/scan。
- **占比高不等于能优化**——scores/output 占比大也可能是 FLOPs 绑定的物理上限，先读源码判断
  有没有改动空间，不要为了"动了点什么"硬改一个已经最优的 kernel。
- 同 PK-07：不要顺手修正确性、缓存键必须 O(1)、`bd` 对比一份 build 一个进程、不碰 BF16
  独立写集、精度判据不放松。
- 这个基线（"GDN 方程成本基线"）本身是人造对照，**不代表速度门槛或优化目标**——PK-03 验收
  时写的"无速度门槛"依然适用，本任务的目标由 PM 看 GDA-05 数据后定，不是"追上这个基线"。
